## What this revision actually requires

The [base protocol](https://modelcontextprotocol.io/specification/2026-07-28/basic) and [versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning) make modern requests self-contained: required protocol version and client capabilities in `_meta`; optional client identity; required `resultType`; discovery; explicit application state identifiers; defined modern errors. `initialize` is retained only for legacy compatibility. Connection identity must not become implicit conversation identity.

The [HTTP binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) requires POST request metadata headers and body/header agreement, Origin validation, request-scoped JSON or SSE responses, and disconnect cancellation. It removes modern session IDs, GET notification streams, and resumable SSE. Supporting prior versions remains optional. The [stdio binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio) requires newline-delimited protocol messages, stdout purity, cancellation notifications, and recommends prompt EOF shutdown.

The [caching contract](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching) requires nonnegative `ttlMs` and `cacheScope` on six completed methods: discovery, tools list, prompts list, resources list, resource templates list, and resource reads. Sensitive/user-specific resources belong to private caches, and cache scope cannot replace authorization.

Optional features are conditional contracts, not a checklist of everything to implement. This server exposes tools, resources, and a prompt; SDK serving entries support subscriptions. It does not use elicitation, roots, sampling, task results, MCP Apps, skills extensions, or custom parameter headers. Their capability, MRTR, schema, consent, and security requirements were read, but adding them is not necessary for this release. Roots, sampling, and protocol logging are deprecated; direct DeepSeek API integration already follows the sampling migration direction. The DeepSeek `completion` tool is unrelated to optional MCP `completion/complete` argument suggestions. Sources: [message patterns](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns), [MRTR](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr), [deprecated features](https://modelcontextprotocol.io/specification/2026-07-28/deprecated), [argument completion](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/completion).

## Concrete findings and release conditions

### A1 — Nonexistent conversation resources return success (mandatory correction)

`resources/read` for `deepseek://conversations/nonexistent` returned HTTP 200 with a valid completed resource containing `message_count: 0`. The template callback calls `ConversationStore.get`, which deliberately returns `[]` for absent keys, so it never distinguishes an existing empty conversation from one that does not exist.

The [resource error contract](https://modelcontextprotocol.io/specification/2026-07-28/server/resources#error-handling) requires `-32602` for a nonexistent resource. Add an existence check and throw an SDK MCP error for unknown IDs; retain successful reads of actually stored empty conversations. Verify the behavior through both modern HTTP and stdio/in-memory contract tests, including URI encoding. **Release condition: correct and test.**

### A2 — Invocation rate limiting and remote access boundary (mandatory security disposition)

The [tool security section](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#security-considerations) explicitly requires servers to “Implement proper access controls”, “Rate limit tool invocations”, and “Sanitize tool outputs”. At initial inspection no wrapper invocation limiter existed, and its HTTP runtime authenticated no callers. Arbitrary no-Origin callers able to reach the endpoint could spend the configured provider account, enumerate/read/reset stored conversations, and manipulate provider files.

This is deployment-sensitive. Direct stdio is an intentional single-user process boundary. Loopback HTTP plus Origin validation blocks browser rebinding but is still reachable by local processes. An externally exposed HTTP server needs a documented and verified authorization boundary: an in-server dedicated MCP bearer token or a trusted authenticating gateway whose backend cannot be reached directly. A shared server credential represents one trusted account; it does not establish multi-user conversation ownership.

[OAuth itself is optional](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#protocol-requirements). Missing OAuth discovery/registration is not a universal core blocker; implementing OAuth would activate its full token audience, resource metadata, scopes, and HTTPS requirements. The README describes a separately deployed bearer-protected hosted endpoint, whose gateway and current code have not been inspected here. Do not infer that deployed protection exists in this npm runtime.

**Release condition:** implement bounded invocation admission/rate limiting or document and verify an equivalent enforced boundary; explicitly define local versus remote access control. If adding bearer mode, use a distinct secret from `DEEPSEEK_API_KEY`, verify every invocation/resource request, avoid token passthrough, and permit an explicitly selected gateway mode without falsely asserting that the application authenticated the caller. See [HTTP security](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#security--endpoint) and [state handle security](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#state-handle-hijacking).

### A3 — Cancellation does not reach DeepSeek, and can mutate history afterward (operational correction)

The focused fixture started `chat_completion`, canceled its HTTP fetch, waited 150 ms, and observed the provider fetch signal still un-aborted. Resolving the fixture later wrote user and assistant messages into `cancel-review`. Every provider-backed callback ignores SDK request context, while the provider client creates only its own timeout AbortController. `clear_conversation` also runs before the provider result and needs explicit cancellation semantics.

The reviewer separately exercised a real Node 20.20.2 stdio subprocess against a stalled local provider. After `notifications/cancelled`, the upstream connection remained open. After closing stdin, the child and upstream connection remained alive at 300 ms with a configured five-second provider timeout (the normal default is 120 seconds). The SDK correctly suppressed the canceled request's output and closed its transport on EOF. This independently confirms that retaining provider work is a wrapper issue, rather than a missing SDK EOF handler.

The [HTTP cancellation binding](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#cancellation) mandates treating disconnect as cancellation and forbids further request messages; SDK handles that protocol layer. [Cancellation guidance](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation#behavior-requirements) recommends stopping work and freeing resources, with exceptions for genuinely uncancellable operations. Therefore this is a demonstrated wrapper/operational gap, not proof that every normal JSON response violates a MUST.

Pass `ctx.mcpReq.signal` into provider requests and combine it with the configured deadline across response-body consumption. Check cancellation before committing conversation state; do not translate caller cancellation into misleading provider-retry advice. Apply this to resource-backed `/models` reads as well as tools. **Release condition: fix or explicitly accept and document continued provider work/state effects; the recommended fix is small and testable.** Verify abort before headers, during SSE, during body decoding, and no post-cancellation history mutation.

### A4 — Advertised resource list changes miss conversation-store mutations (SHOULD correction)

SDK defaults advertise `resources.listChanged: true`, and the subscription was acknowledged, but adding a conversation through the tool produced no list-change frame. Creating and resetting conversations alter the list supplied by the resource template without calling SDK notification APIs.

[Resources list change behavior](https://modelcontextprotocol.io/specification/2026-07-28/server/resources#list-changed-notification) recommends notifying when that advertised list changes. Set `resources.listChanged: false` if no event source is implemented, or emit changes from a shared store event source into every active HTTP subscription. Calling only the per-request server instance is insufficient if subscriptions live on other SDK instances. Zero resource-list TTL reduces staleness but does not fulfill the advertised notification behavior. **Release condition: make the advertisement truthful or wire and test events.** Per-resource `subscribe` is not advertised, so adding individual resource update support is unnecessary.

### A5 — Output handling and JSON text fallback need explicit assurance (bounded follow-up)

Outputs are constructed as typed text/JSON blocks, raw responses are opt-in, and tool errors include actionable details. No HTML execution or provider credential passthrough occurs in the wrapper. However arbitrary model text, provider error messages, and optional raw payloads are forwarded without a dedicated secret-redaction/bounds policy. The tool security requirement should be satisfied by documenting and testing the actual trust boundary rather than stripping arbitrary model prose. Ensure provider errors cannot echo configured credentials and apply practical payload limits. Serialized structured JSON in a text block is recommended for compatibility; several tools emit only a human summary instead of the complete structured value. This is a SHOULD improvement, not a reason to remove existing summaries. [Source](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#structured-content).

## Source inconsistencies that must not become invented implementation requirements

The dated overview still mentions extension negotiation during initialization, while the detailed versioning/schema establish per-request negotiation. The subscriptions page recommends a graceful completion result on server shutdown, whereas the cancellation page requires server cancellation notification when tearing down subscriptions; the schema describes server cancellation as stdio-only. Read the detailed binding and schema together and do not infer that shutdown behavior has been independently proven for every transport. The schema reference also contains an illustrative read result without required caching hints; the actual `ReadResourceResult` inherits required fields. Examples are not permission to omit normative fields.

These editorial tensions were observed directly in the reviewed pages. They do not justify reintroducing sessions or adding unsupported client features.
